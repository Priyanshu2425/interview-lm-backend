Setting up

Lane A needs nothing but the database. Lane B needs the API and a real bearer token — there is no development bypass, which is worth knowing before you try to curl anything.

Get a bearer token

Every Candidate-scoped route depends on current_candidate and none takes an id from the caller. There is no dev bypass, so Lane B needs a genuine Gatehouse token.

  1. Run backend/scripts/dev-auth-setup.sh once (idempotent).
  2. Start the surface: cd frontend && npm run dev, with VITE_API_URL pointing at localhost:8000.
  3. Sign in at https://interview-lm.dev.buildspacelabs.com:5173.
  4. DevTools → Network → any /v1/ request → copy the Authorization header value.

export API=localhost:8000

Decisions, not defects

Worth your eyes

Four things that are working as built but were judgement calls. None is a bug; each is somewhere the shipped behaviour differs from what you might reasonably expect.

W1 · The planner's call dilutes a reading in the Operator console

SPEC-0005 forbids an unattributed model call, but at planning time no Topic Visit exists yet — the plan is what decides Visits exist. The call is attributed to plan_<session_id>.

Consequence: the Operator console's count(distinct topic_visit_id) counts one extra unit per Session, so credits_per_visit reads slightly low. The clean fix is a call_record.kind column, which is schema work ISSUE-0041 correctly declined to open unasked.

W2 · MCP's open-Visit guard is no longer enforced by the store

uq_visit_one_open_per_session narrowed from state IN ('open','answered') to state = 'open'. It had to: with no grading between questions, a Session's second question collides with its own first answered row.

But that index carried the comment "a partial unique index is what makes that a property of the store rather than a request to a ReAct agent". For MCP Mode, that rule now lives in McpServer via visits.unresolved — application code, in the one mode whose host is an agent nobody controls. Recoverable by denormalising session.mode onto topic_visit.

W3 · topic_visit.exchange and the graded state are still here

ISSUE-0039 specified removing both. They stayed, because MCP Mode still writes and reads them. Retiring them would have broken MCP silently, so both columns carry a comment naming the slice that may finally retire them.

W4 · Production has not been migrated

Every one of these changes has been proven against local Postgres only. The shared Neon deployment still runs the old schema, and its stored credential currently fails authentication. Migrating it needs a written plan and a dump first — neither exists yet.
