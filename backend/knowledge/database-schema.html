The InterviewLM Database Map 🗺️

Every table, every column, and the path a request actually takes through them — from a Candidate's sign-in to a graded Topic Visit.

System flow interview_lm_core interview_lm_content interview_lm_graph Cross-schema rules

One Postgres instance holds three schemas, and each one has a different lifecycle — how long its rows are meant to live, and what's allowed to delete them.

interview_lm_core — permanent Candidates, Sessions, Evidence, credits, identity. Nothing here is ever dropped. A trigger, not a convention, enforces that.
interview_lm_content — disposable The Corpus: notebooks, sources, topics, chunks. Rebuildable by re-import. Deleting it never touches core.
interview_lm_graph — framework-owned LangGraph's own checkpointer tables (not defined by this app). Lets a parked Session resume exactly where it left off; can be dropped wholesale outside the resumption window without touching anything else.

Sign in through Gatehouse

Gatehouse issues a JWT (iss, sub, aud=interview-lm). Every API call verifies it locally against a cached JWKS — the app never calls Gatehouse per-request. IdentityStore.resolve(issuer, subject) finds or creates the linking row.

Visit a Topic

One Topic Visit opens per Topic per Session (never twice), and only one may be open at a time — a partial unique index makes that a property of the database, not a rule an agent has to remember. The provider is locked in on the first LLM call.

Grade it, permanently

Exactly one Evidence row is produced per Visit, snapshotting the score, rationale, and citations at that moment — so it still reads correctly even after the notebook that produced it is deleted. Its score deltas then update the Candidate's running per-Topic confidence.

Meter every call

Each LLM call (question-writer, interviewer, judge) is logged with cost and outcome. If billed against platform credits, a matching debit lands in the ledger — idempotent by a unique index on the call id, not an application-level dedup check.

Checkpoint the conversation state

LangGraph writes its own state under the Session id as thread id, so a parked Session — waiting on the Candidate, or recovering from a provider error — resumes exactly where it stopped. This schema is disposable and can be dropped wholesale without touching anything else.

interview_lm_core permanent

Everything that must never disappear on its own: who the Candidate is, what happened in every Session, the graded record of every answer, and every credit ever spent. Constraints here are enforced by the database itself — triggers and unique indexes, not application code — because an MCP agent talking to this system is code the team doesn't control, and a database constraint is the one thing a prompt can't argue its way past.

    interview_lm_graph framework-owned

    Not defined by this app. These four tables — checkpoints, checkpoint_blobs, checkpoint_writes, checkpoint_migrations — are created entirely by LangGraph's own PostgresSaver.setup(). The app treats this schema as a sealed box: it only ever creates it wholesale or drops it wholesale, never reads an individual column.

    checkpoints / checkpoint_blobs / checkpoint_writesLangGraph's conversation-state snapshots

    Every step of the interview's state machine, keyed by thread_id = session_id, so a parked Session — waiting on the Candidate's next answer, or recovering from a provider failure — can resume exactly where it stopped.

    Why it's routed to a direct connection: LangGraph's saver uses prepared statements and pipelining that a transaction pooler (like Neon's pooler used for the rest of the app) can't support reliably — so this schema alone talks to Postgres directly, not through the pool.
    Why it's safe to drop wholesale: it's explicitly disposable outside the resumption window. Dropping the entire schema and recreating it touches nothing in core — that boundary is exactly what the app's own migration tests verify.

    Cross-schema rules worth knowing

    The design decisions that explain why the schemas are shaped this way.

    No foreign key crosses a lifecycle boundary topic_visit.topic_id, evidence.topic_id, call_record — all reference Corpus ids as plain strings, never as a FK into content. That's deliberate: a Topic can vanish from content entirely while the permanent evidence row that graded it — with its snapshotted citations — stays fully readable.
    identity is the only place a third-party subject is stored Everything else is keyed on the locally-minted candidate_id. Merging two identities into one Candidate never has to touch Evidence, the ledger, or confidence scores.
    Append-only is enforced by the database evidence has a trigger that rejects UPDATE and DELETE outright. credit_ledger and pool_ledger simply have no code path that updates a row — only inserts, made idempotent by partial unique indexes rather than an app-level check-then-insert.
    topic_confidence is the one mutable table Every other row in core is either immutable by trigger (session, evidence) or append-only by convention (the ledgers, call_record). This is the single exception, and it's called out as such in the code.
